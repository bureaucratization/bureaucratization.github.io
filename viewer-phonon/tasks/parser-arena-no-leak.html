Description

Description

Addresses P2 (rt-safety audit F-7). parse_program performs two Box::leaks per parse (src/compositional_parser.rs:586 and :632) — leaking the preprocessed and expanded source strings. Every live edit/reload calls parse_program, so a long session of hundreds of edits grows resident memory without bound, eventually contributing to paging/instability.

See docs/audits/rt-safety-2026-07.md §4 F-7 and docs/audits/improvement-plan-2026-07.md P2.

Scope / Constraints

  • Files: src/compositional_parser.rs only (+ a test). Do not change parser output/semantics.
  • Give the parser an owned-string arena tied to the compiled graph lifetime, or restructure to borrow from a caller-owned String instead of leaking to static.
  • Behaviour must be byte-for-byte identical (same parse results); this is a memory-lifetime fix only.
  • Implement directly — do not decompose further.

Reproduction

Leak accumulates over many parses. A regression can either count leaked allocations directly or measure RSS/heap growth across N repeated parse_program calls (soak-style).

Validation

  • Failing test first: a regression that parses the same program N times (e.g. 10_000) and asserts bounded memory — the two Box::leak sites currently make per-parse leaked bytes grow linearly; assert no unbounded growth after the fix (leaked-bytes counter or a before/after RSS bound).
  • Fix: replace both Box::leak sites with an owned-string arena / borrowed lifetime.
  • Post-fix: parse results unchanged (existing parser tests green); repeated-parse memory bounded; cargo run --release --bin glitch_stress -- --seed 42 still exits 0.
  • cargo build + cargo test pass with no regressions.
