Make build admission follow worker slots and expose throttling in status/TUI

Description

Remove the surprising hidden serialization of ordinary full-execution workers and make resource admission understandable in every primary operator surface.

Change the semantic default so that when dispatcher.resource_management.max_build_agents is not explicitly configured, its effective value follows dispatcher.max_agents. An explicit lower value remains a supported intentional operator throttle. Do not conflate this concurrency override with predictive disk admission: disk_sentinel_enabled=false must continue to disable predictive disk refusal, and status must not report fabricated/projected zero headroom as healthy when no projection exists.

Handle configuration generation and compatibility deliberately. Fresh setup/init/reset/profile templates must not bake in a stale fixed 1; either omit the optional override or render a value derived from max_agents. Preserve explicit user overrides on load/reload. Determine whether legacy generated max_build_agents=1 can be distinguished safely from user intent; if not, do not silently rewrite it—make wg config lint/status explain the active throttle and give the exact opt-out command. Ensure hot reload recomputes the effective cap immediately.

Make admission visible without log spelunking. At minimum, human and JSON forms of wg status/wg service status, the worksgood status/operator flow, and the TUI dashboard/task inspector must expose: effective build-heavy active/max capacity; count of admission-deferred tasks; per-task waiting reason; whether the cap is inherited or explicit; and an actionable command such as wg config set dispatcher.resource_management.max_build_agents <N>. A task that has never attempted because of resource admission must not look like an unexplained ordinary Open task. When disk sentinel is disabled, say so and render projected headroom as unavailable, not Healthy — 0.0 GiB.

Preserve the good safety properties: admission deferral is not a spawn attempt/failure, consumes no retry/provider-health/review budget, and an explicit cap still dispatches deferred work exactly once when capacity opens. Keep output concise in the no-pressure case.

This task is sequenced after setup route activation and Pi accounting/review visibility because it may touch the same config/status/TUI/help surfaces.

Validation

  • With max_agents=3 and no explicit max_build_agents, three build-heavy fixtures may dispatch concurrently; effective config/status reports 3, inherited from max_agents.
  • With explicit max_build_agents=1, the second fixture is admission-deferred without an attempt and all required CLI/TUI/JSON surfaces identify 1/1, the affected task, the reason, override source, and exact remediation command.
  • Changing max_agents while the build override is unset updates the effective heavy capacity; changing an explicit build override by hot reload takes effect without daemon restart.
  • Fresh setup/config/profile output no longer silently serializes workers at one; legacy explicit configuration is preserved or migrated only with provenance-safe rules.
  • Disk-sentinel-disabled status never claims meaningful zero projected headroom.
  • Existing admission neutrality/exactly-once smoke coverage remains green; add deterministic terminal/TUI regression coverage for operator visibility.
  • cargo fmt --check, targeted tests, cargo clippy, owned smoke scenarios, and git diff --check pass.
