Description

Found while working on prune-stale-worktrees. wg disk cleanup --execute lists stale caches as "eligible — every owner passes all removal guards" but then reaped=0/freed=0: removal of paths containing 555-mode directories (WG deliberate .wg-owned-baseline baseline protection, e.g. .wg/build-tmp/agent-116, /tmp/wg-cargo-tmp-agent-17) fails with "remove failed: Permission denied (os error 13)" and is silently preserved. The stale count in wg status stays at 20 indefinitely even though every owner is dead and the task is terminal. Either the cleaner should chmod-unlock WG-owned baseline dirs before removal (respecting the .wg-owned-baseline marker it wrote itself), or it should classify these as protected-by-design and stop counting them as stale-eligible noise.

Related second finding: 31 orphaned smoke-harness processes (hung 11+ days, cwd in deleted worktrees of dead agents) kept the "owning worktree still has a live process/cwd/open file" guard tripping, blocking ~26 GB of stale build-target layers from reaping. Consider recording agent spawn pgids and reaping descendant process groups on agent death/reap.

Validation

  • Reproducer: create a stale agent cache containing a 555-mode .wg-owned-baseline dir, run wg disk cleanup --execute, observe reaped=0 + "remove failed"
  • After fix, either the protected cache is reaped (marker-owned dirs unlocked and removed) or it is reported as protected-by-design and excluded from the stale-eligible count
  • wg status disk stale count reflects reality after cleanup
  • cargo test --lib green; no unrelated production changes
