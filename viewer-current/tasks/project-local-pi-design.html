Objective

Turn the attended proposal into a concrete, compatibility-aware design for Pi-only workflows. Audit the current implementation first: project profile associations and fingerprints, global/local merge rules, setup defaults, config source reporting, migration, Pi plugin setup, identity/federation storage, and checked-in .wg behavior.

The design must decide precisely:

  • which settings are project-owned and which, if any, may still inherit globally;
  • how wg profile select applies a reusable ~/.wg/profiles/<name>.toml definition into deterministic project state without erasing local guardrails or importing unrelated settings;
  • how an existing project with no local route behaves when stale global routing exists;
  • compatibility/deprecation behavior for wg profile use and explicit global operations;
  • the safe migration that removes only stale global routing/profile activation while preserving reusable profiles, secrets not owned by routing, and all identity/federation data;
  • what source/provenance output every effective-setting surface must expose.

Produce docs/design-project-local-pi-config.md with a phased implementation plan and explicit acceptance matrix. Prefer a clean cutover over adding another ambiguous precedence mode.
