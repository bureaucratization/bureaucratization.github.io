Deferred followup — NOT part of V1 release recovery

User-directed scope reduction: keep this task paused/unpublished. Do not dispatch it merely because the source-retry implementation finishes. V1 ships bounded source retries plus minimal status/next-action output in the implementation task. This broader proposal requires a later explicit prioritization decision based on usage. Historical proposal below is retained as design context, not an instruction to implement now.

Integrate the provider retry scheduler with completion-review, bounded/deep evaluation, and Agency outcome projection without making evaluation a second scheduler.

When source failure evidence already proves a retryable provider/infrastructure condition, record/project a typed retry recommendation with failure class, evidence ID, retry count, next eligible time, and exact route, but do not launch a semantic evaluator and do not record a synthetic quality score. If a reviewer/evaluator itself fails for provider reasons, preserve the exact candidate and evaluation identity and schedule only that evaluation stage after falloff; do not rerun source or re-evaluate unchanged bytes through a new record. Semantic rejection must remain semantic and must not auto-rerun merely due to time.

Ensure show/list/status and Agency learning distinguish infrastructure-unavailable/retry-recommended from a scored quality failure. The planner remains the sole owner of deadlines and automatic rerun effects; evaluation only records bounded evidence and recommendations.

Validation

  • Direct provider failure produces no evaluator model invocation and no quality score, but exposes a retry recommendation tied to exact evidence.
  • Evaluator infrastructure failure retries the same exact candidate/evaluation record after its deadline, at most once per due effect.
  • Source work is not rerun for evaluator-only failure.
  • Semantic reject never enters provider backoff and unchanged bytes are not re-evaluated.
  • Exactly-once Agency projection does not count repeated provider receipts as repeated performance failures.
  • Restart/replay preserves recommendation identity and does not duplicate evaluation or learning records.
  • cargo fmt --check
  • Targeted completion-review/evaluation/agency tests pass.
  • git diff --check

Release-batch execution constraints

  • Inspect and reuse retained worktree commits before editing; merge current main through supported worker flow. Do not discard WIP or historical receipts.
  • Remain Pi/Codex on the project exact route; no provider/model fallback and no WG credentials.
  • No global cargo install, daemon restart, root-checkout merge, or origin/main push from workers; the attended operator owns deployment. Use explicit candidate binaries and project-local build scratch.
  • Tests/smoke changes must follow the existing real-entry-point smoke contract; mocks/fake-clock cases are integration tests unless the existing harness explicitly permits them.
  • Any user-visible retry/cleanup changes require live or scripted terminal/TUI human-flow validation, not only unit tests.
  • Capture executed validation as immutable evidence through supported mechanisms without inventing hard gates or demanding this task own future review/publication receipts as candidate input.
