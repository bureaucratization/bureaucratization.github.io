Description

User decision

Make project configuration the single authority for model routing. One default route; strong and weak are EQUAL BY DEFAULT and split only when explicitly configured. Optional explicit role overrides remain supported. One resolver shared by dispatch, workers and review. Supervisors must not resurrect stale model overrides. New attempts use the current configuration revision; existing attempts keep their pinned route. Missing/unsupported routes block admission visibly before consuming/failing tasks. Preserve current project Pi/Codex Sol/Luna selections as intentional explicit splits; do not change operator routes while implementing/testing.

Concrete incident and diagnosis discipline

User reported another project whose worksgood.toml routes disagreed with a supervisor respawning stale --model pi:lunaroute:glm-5.3; Pi review subprocess rejected Unknown provider, while source dispatch reported WG-EXEC-ROUTE-MISSING role=default. These are different error layers. Reproduce the stale supervisor override and trace the missing-route path independently; do not assume an unsupported provider alone explains a missing configured value. User also needed a restart for a cold Cargo baseline; that is a separate downstream task, not a reason to entangle model routing with build resources.

Scope

  1. One canonical project route resolver/revision used at all production entry points, including startup/reload, supervisor replacement, task default/worker, FLIP inference/comparison, Eval and agency one-shots. Reuse current project-local configuration authority and provenance instead of a new store. Global profiles may remain reusable templates, not competing execution authority. Preserve existing documented worksgood.toml/.wg/config.toml precedence and migration rules, fail loud on ambiguity.
  2. Default inheritance is dynamic: unset strong inherits project default, unset weak inherits strong, unset role inherits its designated effective tier. Explicit weak and explicit role overrides win only where declared. Choosing one model must NOT require writing sixteen roles or implicitly install a cheap/Haiku/other-provider weak route. Changing inherited strong changes inherited weak; explicit weak remains unchanged. Provide an explicit reset-to-inherit operation in the existing tier/profile surface, do not require hand-editing config. Preserve existing intentionally explicit unequal tiers. Do not flatten existing pinned FLIP-vs-worker policy or silently discard role overrides. Provenance must distinguish inherited vs explicitly selected values.
  3. Supervisor is process supervision only. It reloads current project selection for each new daemon and must not persist/replay stale model overrides as routing authority. For explicit user service start --model compatibility, apply route selection through the SAME project-local config path before launch with a clear notice; no hidden supervisor override survives. Existing stale supervisor state must be detected and reconciled against authoritative local config with a visible migration warning; do not overwrite valid newer file routes. Reject any ambiguous migration requiring a decision rather than silently choosing an old route. Reload/supervisor respawn/concurrent next-attempt resolution use a coherent configuration revision; active attempts remain exactly pinned.
  4. Missing local route and unsupported Pi provider are separate typed admission blockers with exact role, effective route if any, config source/revision and one corrective action. Neither should mark a never-started task as a failed work attempt. Do bounded capability validation using the ACTUAL Pi invocation/provider-registration context for workers and hermetic review; do not consult a divergent WG provider allowlist or add a billable model call per task. Preserve hermetic review/no task-context leakage. If custom provider support cannot be shared safely, reject that selected route early with an actionable message naming the affected lane. Do not silently switch providers or use WG credentials.
  5. Status/show/config output makes project default, effective strong/weak, explicit overrides, source and active revision clear. Show configured-vs-running attempt pins as intentional rather than an unexplained disagreement. Updates unblock route-paused admission on subsequent ticks without manual task retry or daemon restart once a valid selection is supplied.

Validation contract and evidence

The operator-assigned validation_command explicitly captures fmt/clippy, config library tests, supervisor tests, and the existing project-local/two-tier/profile-pinning/dispatcher-roundtrip/setup integration targets. Put the new end-to-end fixtures in those exercised integration targets (or request a specific gate addition BEFORE review if a new target is necessary). Use real CLI/PTY and daemon/supervisor entry points within disposable HOME/projects and register applicable owned smoke; mock provider metadata only where integration-test policy allows, distinguishing it from live Pi capability proof. Do not claim green worker logs are authoritative candidate evidence. No self-future hash/receipt requirement in reports. Exact reviewed candidate evidence is captured by the host.

Validation

  • Fresh project with ONE default resolves every unset role and both tiers to that route; does not require a WG global config/key or write sixteen role entries. Python/non-Rust disposable repository works too.
  • Set weak separately, change strong, reset weak to inheritance: explicit split persists until reset, then tracks strong. Explicit role override wins only for that role. Existing intentional project Sol/Luna split and historical attempt routes remain unchanged.
  • Two independent projects and global profile/credential fixtures remain isolated under setup/config/profile/start operations; inspect actual bytes and winning-source output.
  • Real supervisor starts with A, project changes to B, reload and supervisor-driven daemon replacement both use B for new work while a running A attempt stays A. Stale persisted launch state cannot reintroduce A. No model call occurs under the wrong route.
  • Missing route versus unsupported provider are distinguished before lifecycle attempt consumption. Correcting config resumes admission once, without wg retry/service restart. Cold build admission is not mislabeled as a route error.
  • All worker/review lanes use the same canonical route and provider capability context; unavailable/unsupported explicit weak route is not silently downgraded to strong/Claude/another provider.
  • Actual terminal flow demonstrates default-only setup, optional split/reset, configuration provenance and actionable route blocker. Add and execute it inside configured integration targets so immutable output contains real human-flow evidence.
  • Full configured validation command passes with exact candidate-bound receipts, existing negative security/isolation tests retained, and no gate exclusions. Fix relevant fixture isolation at disposable test-child boundary only.

Execution discipline

Single focused implementation, not a broad new architecture phase. Send an early concise message naming resolver/supervisor seams and chosen inheritance migration. Preserve old receipts, task history, source work, and exact runtime pins. Managed worktree only; canonical project scratch outside protected worktree .wg; no global install, live daemon restart, root-checkout merge or origin/main push. Do not embed Cargo commands in generic product prompts or route logic: validation here is WG-repository policy. Operator owns coordinated deployment. If additional checks need authoritative capture, request their exact commands early instead of repeated unchanged FLIP submissions.
