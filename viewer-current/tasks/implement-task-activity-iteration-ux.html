Expose embedded task activities and complete iteration history

Description

Implement the task activity and iteration UX selected after the evaluation-cutover audit. Keep the primary graph/list visually task-centric: assignment, FLIP inference/comparison, evaluation, and related internal work are not ordinary task rows and must not appear to own dependencies or lifecycle state. Instead, show a compact, quiet parenthetical activity strip on the real task row when activity exists, e.g. (assign ✓ · flip ✓ · flipx ✓ · eval ✓ · iter 2), with accessible text/legend and clear pending/error/reject states. Avoid unexplained abbreviations where space permits.

Make the complete history discoverable by expanding the real task in TUI and through a canonical CLI/JSON surface. Present a nested chronology that preserves distinct identities and semantics:

  • task lifecycle generation/revision;
  • execution attempt and fence;
  • immutable candidate/manifest revision;
  • assignment/review activity attempts bound to the appropriate task attempt or exact candidate;
  • explicit structural cycle iteration, when configured. Do not flatten all of these into one ambiguous integer called iteration. The compact row may show a human summary, while the inspector/history view names each layer precisely and retains superseded/rejected/error attempts rather than overwriting them.

Use the non-authoritative activity projection decided by audit-evaluation-evolvability-cutover and the accounting/receipt seams from fix-pi-accounting-review-visibility. Storage may be append-only activity/event records with indices, but presentation should feel embedded in the parent task. Completion broker/lifecycle kernel remain the sole authority for source transitions. Default wg list --all remains one row per task while indicating that internal activity ran; an explicit activity/history option may enumerate records without pretending they are graph tasks.

Coordinate with the admission-status TUI changes already sequenced ahead of this task and preserve compact layouts, narrow terminals, accessibility, stable JSON, and performance on large histories.

Validation

  • Default CLI/TUI lists render one row per real graph task and a compact parenthetical activity summary only when applicable; no assignment/FLIP/eval activity masquerades as a task or dependency.
  • Expanding a task and the canonical CLI/JSON history surface expose every generation, execution attempt/fence, candidate revision, internal activity attempt, receipt/findings reference, route, timing, verdict/error, and separate usage/cost.
  • A fixture with an initial rejected candidate, repair/retry, and accepted replacement visibly retains both histories and binds each review to the correct immutable candidate.
  • A fixture with a structural cycle and worker retry labels cycle iteration, lifecycle generation, and execution attempt distinctly.
  • Pending, infrastructure-error, semantic-reject, superseded, and pass states are visually and machine-readably distinct.
  • Help/legend explains parenthetical labels and how to open history; narrow-terminal snapshots remain readable.
  • Relevant targeted tests, terminal/TUI smoke scenarios, cargo fmt --check, cargo clippy, and git diff --check pass.
