Description

Objective

Implement the user-approved execution-contract experiment in WG itself after the existing reliability chain. Preserve the durable graph, history, claims, dependencies, artifacts, task state, service and TUI. Do not create another work coordinator. Reuse the accepted prove-pi-process-wakeup results; do not repeat that project as a separate architecture.

The specific defect to eliminate is loss and reconstruction of execution identity: profile/role resolution produces provider+model, a downstream caller receives only the bare model, then another component guesses a handler again. Historical specimen: WG_EXECUTOR_MODEL_MISMATCH_TRIAGE.md. Treat its historic scenario as supplied design context, not a requirement to manufacture a new historical receipt.

Hard boundary

AUTHORING: explicit project selection, reusable profiles, role/tier overrides and legacy migration conveniences resolve ONCE into a complete ExecutionAssignment: task identity, agent identity, exact execution selection and reasoning. Existing required attempt/config-revision/fence fields remain binding. Strong and weak default equal; explicit split/role overrides remain intentional. Global authoring conveniences must not regain hidden project execution authority.

RUNTIME: consume the immutable assignment. Execution is conceptually Pi { opaque_route, reasoning } or Shell { argv }. Recognize the outer Pi envelope once; everything after pi: is opaque to WG and passed unchanged to Pi using safe argument/API handling. No provider-specific fields are needed in the canonical Pi runtime assignment. WG may preserve/display/compare/pin the string; it may not split the inner selection, normalize model names, consult registries, infer handlers, merge profiles, resolve tiers or silently select a fallback after assignment. Reasoning is separate and pinned; no provider-specific reasoning dialect inference inside WG.

Pi owns provider/model resolution, authentication, endpoints, capability discovery and execution. Optional preflight asks the SAME actual Pi runtime/configuration that will launch the worker/reviewer. Its structured outcome must distinguish missing required capability/configuration from transient failure. An unrelated optional tool must not become a WG-global startup prerequisite. Never consume task/cycle retries for unchanged invalid admission configuration. If Pi cannot isolate an optional capability failure, surface that bounded limitation before admitting work; do not teach WG provider semantics to compensate.

The supervisor restarts processes using the current project assignment policy, never an independent cached model override. Running/resumed attempts keep their existing assignment; changed config applies to new assignments. Migration of a running attempt requires explicit new authority, not reinterpretation. Worker, review, evaluation, retry and recovery paths must all respect this boundary. Each review execution may have its own resolved role assignment, but it is resolved once and then immutable as well.

Experiment scope

Use a small explicit opt-in experimental path or equivalent controlled branch boundary so the existing deployment is not silently switched. Remove legacy routing from the experimental runtime path rather than merely layering a new wrapper over it. Retain read-only compatibility for historical executor/provider/model fields. Active legacy configurations need an explicit loss-aware migration or actionable refusal, never a guessed native-to-Pi translation. Do not delete histories, identities, credentials or optional external features. If an execution mode such as remote provider dispatch is outside this experiment, state its unsupported boundary instead of rerouting it through Shell covertly.

No new scheduler, model registry, provider allowlist, agent hierarchy or mutable route projection. Preserve existing process ownership, cancellation, leases, publication and evidence protections. Keep generic runtime free of Cargo-specific policy.

Validation

  • Authoring tests produce one executable assignment, with default-equal tiers, explicit overrides, config revision and stable attempt pinning. Two projects stay isolated.
  • Runtime tests pass unusual but Pi-addressable opaque selections unchanged from assignment through actual launch, preflight and recorded identity; configuration mutation/daemon restart cannot cause re-resolution for an existing assignment.
  • Unsupported Pi selection is diagnosed by Pi, not WG name heuristics; bad unrelated optional tool configuration cannot silently kill useful work and consume three cycle retries. Use controlled Pi fixtures for rejection/race cases and label those separately from real Pi proof.
  • Source and actual launch-path regression show no handler_for_model, registry lookup, backend inference, tier/profile merge or provider-specific fallback reachable after the experimental boundary. Historical gpt-model/Claude mismatch is unrepresentable in that path without relying on a blacklist.
  • Real CLI/daemon flow exercises task creation, role selection, preflight, worker launch, review assignment, cancellation, restart and appropriate completion with exact route preserved. Reuse current wakeup/candidate-evidence mechanisms, no duplicate receipt machinery.
  • Existing supported default path and history readers remain compatible; experimental opt-in and unsupported legacy settings are visible. Record removal/migration seams briefly in developer docs.
  • Run applicable checked-in CI checks and focused regressions through the supported evidence path. Worker-selected checks remain evidence, not silently invented mandatory gates. Real user-facing changes need owned real-entry-point smoke and actual execution evidence, not only a written report.

Execution boundary

This is an implementation experiment, not authorization for a universal rollout. Managed worktree only, explicit candidate binaries and canonical project scratch. No global install, live daemon restart, origin/main push or operator route/credential changes. Do not import unrelated failed branches or expand the earlier CI repair. Reports identify tested versions and implementation boundaries; no candidate future hash, progress-message timing or later review/deployment receipt is an acceptance requirement.
