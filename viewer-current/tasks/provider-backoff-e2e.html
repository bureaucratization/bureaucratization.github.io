Objective

Validate minimal V1 source-provider recovery through the actual dispatcher and generated worker wrapper after provider-backoff-planner. This task does NOT depend on the deferred evaluator integration or rich UX work.

Exercise retryable 429 with Retry-After, eligible temporary outage/transport failure, successful recovery, exhausted attempt/time budget, daemon restart, duplicate/stale failure evidence, manual pause/cancel, hard auth/config failure, semantic rejection, and ambiguous interrupted execution. Controlled providers/fake clocks belong in integration tests where required by smoke policy. Register owned smoke only for actual supported CLI/daemon/terminal entry-point scenarios; use explicit candidate binaries and disposable projects/services.

Prove preserved work and exact route, one lifecycle-authorized attempt per due retry, no budget reset on restart, no premature Retry-After violation, and at most one terminal publication. Source-provider errors must not waste semantic evaluator calls. Reviewer/evaluator-only failures retain pre-existing policy and never invoke the new source-retry path; do not implement evaluator recovery here.

Show the minimal status/next-action flow to a user. On exhaustion the graph must visibly need attention, not masquerade as active progress or a semantic quality failure. Teardown must target only owned processes. Add only focused fixes exposed by the tests, not broader architecture.

Validation

  • Controlled tests reach every attempt/time bound without wall-clock waiting and prove Retry-After beyond window requests attention.
  • Real dispatcher/worker-wrapper recovery yields one fresh fenced attempt and at most one publication with exact route/work retained.
  • Restart and replay preserve deadlines, used budgets and effect identity; no duplicate model request from a replayed due effect.
  • Semantic rejection, auth/config/credit, authority failure, pause/cancel, reviewer-only failure and unresolved ambiguous outcome do not trigger source retries.
  • Actual terminal flow demonstrates waiting, next eligible retry, recovery and exhausted NeedsAttention with actionable guidance.
  • Tests/smoke ownership is correctly registered for implemented source-recovery surfaces; candidate-binary owned checks pass.
  • cargo fmt --check, cargo clippy, targeted tests, and git diff --check pass; record exact executed evidence and any remaining limits.

Execution constraints

Use the current managed worktree and current main; preserve retained work and immutable evidence. Use Pi on the exact project Codex route with no fallback or WG secrets. No global install, daemon restart, root-checkout merge, or origin/main push by workers. Test explicit candidate binaries with project-local scratch. Capture actual validation through supported immutable evidence APIs; do not invent hard gates or require the candidate own future review/publication receipts as input. Never weaken lifecycle, review, or publication fences.
