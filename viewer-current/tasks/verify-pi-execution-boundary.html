Description

Objective

Independently test the accepted experimental Pi/Shell immutable-assignment path against the existing WG path and direct Pi. Answer whether it actually removes interpretation/configuration failures and operating ceremony without weakening the durable work system. Do not start another architecture rewrite or enable it globally.

Use docs/reliable-work-guiding-principles.md and the preceding task hard boundary. Hold the model, task, relevant runtime tools and configuration as comparable as possible. Record mismatches honestly; direct Pi is an execution control, not a replacement for WG graph semantics. Include a neutral non-Rust task. Reuse previously captured valid wakeup evidence where exact runtime identity matches; do not multiply long model runs solely for report ceremony.

Validation

  • Comparative actual CLI/daemon/Pi runs cover useful work, long managed wait/wake, cancellation, restart, configuration changes, missing/unsupported selection and an unrelated optional-tool misconfiguration.
  • Trace intended assignment versus actual launch and continuation for worker and review; opaque inner selection remains unchanged. No post-assignment profile/tier/registry/backend inference occurs.
  • Invalid configuration is an admission blocker, not wasted work/cycle retries; optional capability isolation or its explicit unsupported limitation is demonstrated rather than claimed.
  • Verify task ownership, saved work, evidence integrity, strict-versus-advisory review policy and publication safety remain intact. No duplicate command or publication, orphaned owned process or revival after cancellation.
  • Report model/runtime versions, meaningful outcomes, elapsed time/cost where available, human interventions, retries and unresolved blockers. Distinguish passing controlled fixtures, actual Pi proof and unsupported cases.
  • Give a concise go/no-go recommendation and exact remaining migration/deletion boundaries. A no-go finding is a valid evaluation result, not a reason to alter evidence until the experiment looks successful. Automated rollout is NOT authorized by the recommendation.
  • Any small directly related correction has its own focused regression and applicable repository checks; substantial product changes are returned as a specific decision. Use supported evidence capture, not new mandatory hard gates or future self-receipts.

Managed disposable projects/worktree and explicit candidate binaries only. No live configuration changes, global installs, main publication or second process manager. Operator owns any subsequent rollout decision.
