Description

Result

Finish the missing generic validation boundary: a worker can select an appropriate check and capture trustworthy candidate-bound execution evidence without turning that check into a mandatory gate or needing the operator to invent one. Required checks still come only from explicit user/repository authority. Reuse existing execution/evidence/completion APIs; do not add a scheduler, another evidence store, or a requirement to know internal receipt commands.

Preflight and completion must agree about required checks, optional worker-selected checks and supported evidence capture. Prose acceptance remains the intended outcome, not an automatically executable command list. Do not infer arbitrary mandatory commands from prose. A required check absent from approved authority yields one actionable contract-correction request before repeated semantic review. Captured optional success is evidence, never permission to waive an existing failed gate. Support reusable results from managed execution only when candidate/command/environment identity and trustworthy execution capture match; otherwise explain why revalidation is needed. No independent requirement to re-run every successful command solely to attach evidence.

Separate intended result/acceptance from coordination guidance at review assembly. Explicitly supplied communication guidance must not become acceptance criteria. Avoid brittle prose heuristics that erase genuine user requirements; ambiguous classifications request a decision. Preserve advisory versus explicitly strict review policy. No silent downgrade of current strict acceptance, no model call solely to rediscover an exit code, and no hard-coded Cargo rules.

Validation

  • Completion canaries exercise a neutral non-Rust task with optional worker-selected check, host-bound capture and ordinary review; no task gate mutation is needed merely to submit evidence.
  • Required failure remains unsatisfied despite optional success; stale/foreign/forged execution evidence cannot satisfy either category. Relevant environment/candidate changes invalidate reuse.
  • Missing required authority returns one precise correction request; approved revision is recorded and invalidates stale binding. No repeated unchanged review loop.
  • Real CLI entry-point fixture demonstrates the boundary and captured evidence; include it in the existing completion canary suite and applicable owned smoke.
  • Coordination-message timing is not a required deliverable; explicit real product requirements remain visible to review. Preserve semantic rejection/intentional stop behavior from the preceding retained help fix.
  • Configured existing CI fmt/clippy/completion-canary checks pass. Additional diagnostics remain worker-selected evidence, not newly invented hard gates.

Scope is the evidence/acceptance interface, not a broad evaluation rewrite. Keep the ordinary worker interface small and document it briefly.

Operating boundary

Follow docs/reliable-work-guiding-principles.md as intended behavior, not an assertion that it is implemented. Preserve required gates, historic receipts, exact attempt/worktree authority, intentional stops and current explicit project routes. No global installs, live daemon restart, origin/main push, destructive worktree resets or changes to live credentials. Use explicit candidate binaries and canonical project scratch outside protected worktree .wg. Do not turn progress-message requests, report timing or future own receipts into acceptance criteria. Request a precise decision when authority is genuinely missing; do not repeatedly submit unchanged inadequate evidence. Keep fixes within this stage and reuse existing mechanisms.

Release scheduling update (2026-09-14)

The baseline passed its checks and landed, but remote CI exposed one service-start fixture regression. repair-service-start-ci now precedes this chain. Implementation stages are released to run serially after that repair using EXPLICIT candidate binaries; the earlier requirement to wait for an installed baseline is superseded for these implementation stages only. Global production deployment remains operator-owned and conditional on green integrated CI. The final first-user-release-rehearsal remains paused for that deployment, and must not claim installed behavior before it exists. No worker installs globally or bypasses current attempt authority.

Explicit review-policy acceptance boundary

The guiding document distinguishes mandatory configured checks from advisory model judgment. Verify all completion/publication paths honor that declared policy: when completion_review_strict is false, an attributed model rejection remains visible but must not silently gain mandatory veto authority; when explicitly strict, semantic rejection and review unavailability retain the declared fail-closed behavior. The currently observed completion_submit path only applies the false flag to unavailability while unconditionally refusing FlipRejected/EvalRejected; trace the full controller/landing behavior rather than patching one error string. Do not relax mandatory deterministic checks or identity/publication protections in either mode. Preserve historical review verdicts unchanged and distinguish policy-authorized completion with advisory findings from semantic approval. Keep existing strict-mode safety regressions by configuring their policy explicitly. Include both modes in the configured completion-canary tests. This is implementation of the already-approved guiding policy, not authority for a worker to change live project policy/configuration or waive the current task own review.
