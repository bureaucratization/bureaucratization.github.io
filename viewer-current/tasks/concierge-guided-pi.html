concierge-guided-pi

Concierge-guided Pi onboarding: make (attended, interactive) walk a brand-new user from zero to a working automation route, with Pi readiness as the first-class step since WG is embedded in the Pi model plane. Build on the interactive tier-selection flow from setup-collects-strong. Flow: (1) PI DETECTED? If the pi executable is missing, print the exact install command (npm install -g @earendil-works/pi-coding-agent, Node 20+ prerequisite) and exit cleanly with 'rerun worksgood setup after installing Pi' — no partial state, matching the existing ATTENDED_TTY / Pi-unavailable fail-clean style. (2) PROVIDER AUTHENTICATED? Run pi's own credential readiness check (pi auth check or equivalent non-interactive probe) across the providers pi exposes; if none is authenticated, print the guided login instruction (run , then /login <provider>, e.g. openrouter — Pi owns the OAuth flow, WG never sees keys) and exit cleanly for the user to return. (3) MODEL RESOLVABLE? Once authenticated, verify at least one model resolves via Pi's offline registry (reuse the existing bounded preflight style; never live-call). (4) Then continue into the interactive strong/weak tier prompts from setup-collects-strong. Every gate is fail-clean with the exact next command printed; no step ever writes config, installs packages, or stores credentials on WG's side — Pi owns auth, WG only detects readiness. Pin the gate matrix with unit tests (pi missing / pi present + no auth / auth + no resolvable model / all green) using injectable probe results, and a smoke scenario for at least the pi-missing and no-auth gates via the fake-pi fixture. ## Validation - [ ] cargo test --lib green; new gate-matrix unit tests pass - [ ] Smoke scenario covers the early gates via the sanctioned harness bridge - [ ] cargo fmt --check + clippy clean; README/quickstart updated to describe the guided flow
