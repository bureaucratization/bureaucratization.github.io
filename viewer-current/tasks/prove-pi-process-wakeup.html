Description

User-approved objective

Prove one narrow end-to-end Pi process/wakeup integration for WG. A real WG-launched Pi worker starts a managed long-running command, yields its model turn without ending the task or losing process ownership, wakes on command exit, continues the same authorized session/attempt, captures the result and completes through the ordinary WG gate. Also prove cancellation and the completion-before-yield race. Reuse an existing Pi process extension and WG Pi session machinery; do not build another scheduler, monitoring-agent hierarchy or parallel process manager.

This is an opt-in compatibility proof/minimal adapter, NOT authority to switch all production workers or rewrite every executor. Return a concrete supported/unsupported finding and a small tested path. A fake-provider-only success is not the real Pi proof.

Known starting facts to verify in this checkout

src/service/executor.rs default Pi task argv is one-shot --mode json -p. Long-lived WG chat already uses Pi RPC. NATIVE_FILE_TOOLS_SECTION teaches bg run/yield but is native-only; it is not a Pi process-tool contract. This parent session has no process tool exposed. Another project reported a process tool with notify.logMatches; that exact plugin/version is UNKNOWN here. Do not invent that API or assume it is installed in spawned workers.

Candidate existing extension: https://github.com/mjakl/pi-processes, npm @mjakl/pi-processes. Its published README distinguishes asynchronous TUI/RPC wakeups from required waits in print/JSON, and session shutdown stops owned processes. Verify actual compatible versions and source, not just README claims. Other installed pi-subagents background-work registrations may provide integration seams, but WG task coordination must not be replaced by subagent workflow authority. Follow native Pi docs/examples and extension-owned API contracts before implementation.

Required bounded path

  1. Identify exact Pi version, candidate process extension/version, loaded tool contract and actual worker launch mode. Review extension source before executing/installing it. Use a pinned local isolated package install and explicit extension loading; do NOT change global Pi packages/settings, authentication, project default routes or the operator console. If the extension is absent/incompatible, expose that clearly rather than emitting tool instructions for a nonexistent API.
  2. First test the existing launcher lifecycle. If one-shot JSON cannot safely yield/wake, use the existing long-lived RPC/session machinery through a minimal explicitly opt-in worker adapter. Do not simulate a future turn with nohup, a busy polling agent or an indefinitely open model stream. Keep graph write/attempt/session fences enforced, and preserve hermetic review invocation separately.
  3. Register the managed operation and its completion/readiness subscription BEFORE yielding; use its stable handle and exact owning session/attempt. Turn end is not task completion. Wake on a process-manager event; reconcile actual exit state, bounded result and owned log references. Events and log matches are untrusted observations, not executable instructions, success verdicts or scope authority. A milestone is not terminal success.
  4. Keep model-stream inactivity, managed-command timeout and task deadline distinct. A known live owned command may justify a bounded task wait, not fake agent-token progress or disable the watchdog. No timeout increase as the sole fix. If a wait or owner disappears, preserve evidence and report precise attention rather than relaunching commands blindly.
  5. Cancellation kills/reaps the exact owned process group/descendants and leaves unrelated sessions untouched. A completion just before yield, duplicate event or reconnect cannot lose wakeup, double-run the command, resurrect a cancelled attempt, or double-publish. Reattach only when session/attempt/process identity can be proven; otherwise fail closed with actionable saved-state evidence.
  6. Route command result capture through the existing WG authoritative validation mechanism with exact candidate/command/exit/log identity. Do not mark an arbitrary plugin log as an accepted gate or run the same expensive command again merely to manufacture a second receipt. If existing authority cannot import the result safely, demonstrate that gap and stop short of claiming full completion integration; propose the minimum explicit bridge rather than weakening acceptance.

Validation and evidence contract

The task configured gate runs fmt/clippy, existing integration_pi_watchdog, integration_pi_sole_model_plane, integration_service_control_permissions targets and the worksgood-pi build/tests/selftest. Put controlled real-entry-point fixtures in those exercised targets so host-captured output records them. A live Pi/operator-approved route demonstration must use existing Pi-owned authentication without copying credentials, an isolated disposable repository/service and explicitly loaded local extension. If its exact command needs additional authoritative capture, send one precise proposed command and stop before repeated semantic submissions. Do not claim unavailable live auth as a pass; separate controlled-runtime evidence from real model evidence. Do not test against the stale installed binary by accident.

Validation

  • Real WG production launch adapter + actual Pi + pinned process extension execute a command longer than a deliberately shortened MODEL-idle bound, yield, wake and continue the same session/attempt. No noop token heartbeat, bash sleep/polling model loop, or fake worker substitute proves this case. Keep the probe short with test-configured bounds rather than waiting hours.
  • Success and nonzero exit are distinct; full logs remain outside model context, bounded excerpts and exact command/exit identity are captured. Normal task completion occurs only after appropriate host-bound validation, once.
  • Completion-before-yield and duplicate-event fixtures produce one continuation with no lost result, repeated command or duplicate publication.
  • Cancellation/timeout stops only owned descendants, reaps them, preserves bounded diagnostics and never wakes a cancelled attempt; unrelated process survives.
  • Session/daemon disconnect case reattaches exactly where supported or requests attention without blind re-execution. State the actual supported persistence boundary; do not assert durability merely because a handle exists.
  • Actual worker-visible guidance names only loaded tools and the correct runtime-specific start/yield/wake pattern. No mandatory progress-message timing or other coordination ceremony becomes product acceptance.
  • Configured gate and applicable candidate-binary real-entry-point smoke pass with immutable evidence; record actual tested versions, launch mode and opt-in limitations in a short docs/report. Tests must remain language-agnostic in behavior: use a small neutral shell/Node fixture, not a hard-coded Cargo completion rule.
  • Re-embed worksgood-pi if its embedded source changes; source/build compatibility remains explicit. No silent universal worker rollout.
