Deferred followup — NOT part of V1 release recovery

User-directed scope reduction: keep this task paused/unpublished. Do not dispatch it merely because the source-retry implementation finishes. V1 ships bounded source retries plus minimal status/next-action output in the implementation task. This broader proposal requires a later explicit prioritization decision based on usage. Historical proposal below is retained as design context, not an instruction to implement now.

Make provider retry behavior legible and safely configurable across CLI, status/show, TUI, config reference, and operator documentation.

Expose the applied base delay, cap, exponent, Retry-After contribution, deterministic jitter, next eligible retry/probe time, route breaker state, and whether the pending action is source retry, evaluator retry, route probe, or needs-operator. Provide validated duration configuration supporting seconds through days, with a safe bounded default and no zero-delay hot loop. Clearly state that provider failures use direct classification, do not spend an evaluator call, do not change routes, and semantic rejection does not automatically retry.

Avoid creating a second timer or mutable projection authority in the UI. All displays must read verified current-dispatcher retry/evidence state, not retired PlannerStore state. Keep secrets and raw provider payloads out of persisted/displayed diagnostics.

Validation

  • Config accepts documented second/minute/hour/day values, rejects zero/overflow/inverted base-cap values, and round-trips canonically.
  • show/status JSON and human output display the same retry deadline/class/action and route-safe redacted identity.
  • TUI visibly distinguishes cooling down, retry due, probing, evaluator retry, and needs-operator without polling the provider itself.
  • Documentation includes default sequence, cap behavior, Retry-After handling, reset behavior, and operator override/recovery guidance.
  • Existing config and status compatibility tests pass.
  • cargo fmt --check
  • git diff --check

Release-batch execution constraints

  • Inspect and reuse retained worktree commits before editing; merge current main through supported worker flow. Do not discard WIP or historical receipts.
  • Remain Pi/Codex on the project exact route; no provider/model fallback and no WG credentials.
  • No global cargo install, daemon restart, root-checkout merge, or origin/main push from workers; the attended operator owns deployment. Use explicit candidate binaries and project-local build scratch.
  • Tests/smoke changes must follow the existing real-entry-point smoke contract; mocks/fake-clock cases are integration tests unless the existing harness explicitly permits them.
  • Any user-visible retry/cleanup changes require live or scripted terminal/TUI human-flow validation, not only unit tests.
  • Capture executed validation as immutable evidence through supported mechanisms without inventing hard gates or demanding this task own future review/publication receipts as candidate input.
